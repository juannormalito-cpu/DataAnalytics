01

El pipeline

Cinco etapas, cada una con una decisión de diseño real detrás — no un tutorial, un proyecto con los problemas (y arreglos) que aparecen con datos de verdad.

01 · EXTRACT

CSV crudo

493 MB, 6.36M transacciones simuladas de dinero móvil.

02 · SAMPLE

Muestreo

100% del fraude conservado + 1M no-fraude, para caber en el presupuesto de almacenamiento.

03 · MODEL

Star Schema

fact_transactions + dim_time + dim_type. Sin dim_account.

04 · TRANSFORM

dbt (SQL versionado)

17 tests automáticos — unique, not_null, relationships. Reemplaza la transformación en Pandas.

05 · SERVE

SQL · BI · ML

Una misma base alimenta análisis, dashboard y modelo.

Decisión de diseño real

El plan inicial incluía una tabla dim_account. Se descartó: en este dataset, cada cuenta aparece en una sola transacción — una dimensión que no es más chica que los hechos deja de tener sentido como dimensión.

ETL → ELT

Python ya no transforma — solo extrae y muestrea. La transformación completa vive en dbt/models/, versionada en Git y testeada en cada corrida. La orquestación completa (extract → load → dbt run → dbt test) corre con Prefect, con reintentos automáticos por paso — sin Docker, como proceso Python nativo.

02

Modelado de datos

Un Star Schema deliberadamente simple: una tabla de hechos, dos dimensiones. La simplicidad es la decisión correcta cuando los datos no la contradicen.

fact_transactions

1,008,213 filas · monto, balances antes/después, tipo, indicador de fraude, e indicador de inconsistencia de balance calculado en la transformación.

dim_time · dim_type

743 pasos horarios (~30 días simulados) y 5 tipos de transacción (CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER).

05

El hallazgo

Un ROC-AUC de 0.9997 es sospechoso. En vez de celebrarlo, se investigó — y la investigación cambió la lectura de todo el proyecto.

// shap: qué empuja cada predicción hacia fraude o no-fraude
Leakage parcial confirmado

Reentrenando sin origin_balance_delta y balance_mismatch, el ROC-AUC casi no cambia (0.9997 → 0.9992) — pero el F1 se derrumba (0.99 → 0.56). El modelo no estaba "roto" sin esas features, pero el número que más se muestra en un resumen ejecutivo estaba inflado por un patrón sintético del dataset. Documentado en detalle en el manual completo.

El caso interesante: #26

De los 30 eventos, el caso #26 tuvo p=0.6333 — muy por debajo del resto de los fraudes detectados (todos entre 0.99 y 1.0). Es el único caso "dudoso" de toda la corrida, exactamente lo que anticipaba la curva de calibración: el modelo casi no tiene zona gris, así que cuando aparece un caso ahí, es señal de prestarle atención especial.

08

Esto, a escala

Todo este proyecto se armó en una sesión de trabajo. El manual completo documenta cómo el mismo alcance, en una empresa grande, se reparte entre 7 equipos y toma 3 a 4 meses — con revisión de Riesgo, aprobación regulatoria, y despliegue gradual incluidos.

Ninguna de estas piezas corre en la laptop de nadie en producción — cada una tiene su lugar autónomo.
